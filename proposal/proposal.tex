\section{Problem Definition}
Published code capsules often fail to run after release because of dependency rot, undocumented environments, or ambiguous run instructions. Verifying a paper's numbers requires a human to install the toolchain, run the code, and check the output. This project automates that with an agentic system. \textbf{Input:} a code capsule (source plus README and/or Dockerfile) and questions about its reported results. \textbf{Output:} a \texttt{report.json} mapping each question to an answer. \textbf{Success:} every answer matches ground truth under the benchmark's grading rule (\S4). \textbf{Failure:} any wrong answer, a crash, or no file produced.

\section{Motivation and Project Scope}
We target CORE-Bench \citep{siegel2024corebench,corebenchgithub}: 270 tasks from 90 papers (computer science, social science, medicine; Python and R), split 45 train / 45 test, each at three tiers: \emph{easy} (a successful run's output is given, execution forbidden), \emph{medium} (Dockerfile plus README), and \emph{hard} (README only; the agent installs dependencies and infers commands). On the 135-task test split the best published agent (CORE-Agent, GPT-4o) reaches 21.48\% on hard \citep{siegel2024corebench}. The capstone goal is an iterative pipeline that improves on this; this proposal covers the baseline it will be measured against.
\textbf{Scope IN:} Python capsules, CPU-only, small capsules (roughly two-thirds of the test split is under 26\,MB).
\textbf{Scope OUT (deferred):} R capsules, GPU tasks, vision/figure questions, multi-gigabyte capsules, Azure parallel execution.

\section{Runnable Baseline}
The baseline is a single-pass, no-retry pipeline: (1) fetch the capsule, (2) read the README, (3) one LLM call proposing install and run commands, (4) execute those commands once in Docker, (5) one LLM call extracting answers from captured stdout, (6) write \texttt{report.json}, (7) score with the vendored official scorer. No retries, self-correction, or re-planning at any stage.

The baseline is the control for the capstone system, which adds an iterative loop that observes failures, revises commands, and re-reads documentation. Holding model, prompts, and one-shot budget fixed and varying only iteration isolates the loop's marginal value. Single-pass execution attributes each failure to one stage (planning, execution, or extraction). LLM access goes through \texttt{litellm}; the pipeline runs unmodified with an Anthropic or OpenAI key.

\section{Test Case and Baseline Output}
The example is \texttt{capsule-9052293} (1.0\,MB), an ANP-TOPSIS tourism model. \textbf{Input:} the capsule plus the question \emph{``Report the closeness coefficient for location L1.''} \textbf{Expected output:} \texttt{report.json} containing \texttt{0.844703753651819}. All three ground-truth runs are identical, so the prediction interval is a point and an exact match is required. The capsule is run at both tiers.

\begin{center}
\includegraphics[width=0.62\linewidth]{figures/baseline_output.png}\\[2pt]
{\small Figure 1: Baseline output for the same capsule at the easy tier (correct) and the hard tier (incorrect).}
\end{center}

Easy: 2/2 correct, \$0.0034 and 3.0\,s per task.

Hard: 0/2 correct, both failing at execution. The single planning call proposed \texttt{pip install openpyxl pandas \&\& python code/script.py}; the run failed and the pipeline reported \texttt{null}. Manual tracing shows the capsule is reproducible with three sequential fixes, each visible only after the previous failure: (i) \texttt{ModuleNotFoundError: xlrd}; (ii) \texttt{FileNotFoundError}, because the script uses paths relative to \texttt{code/}; (iii) \texttt{XLRDError: Excel xlsx file; not supported}, because \texttt{xlrd}~2.x dropped \texttt{.xlsx} support, requiring \texttt{xlrd==1.2.0}. With all three the capsule reproduces \texttt{0.844703753651819} exactly.

\section{Reproducibility and Run Instructions}
\texttt{pip install -r requirements.txt}, copy \texttt{.env.example} to \texttt{.env}, and set one of \texttt{ANTHROPIC\_API\_KEY} or \texttt{OPENAI\_API\_KEY}. Capsule metadata and prompt templates are under \texttt{examples/}. Docker is required only for \texttt{-{}-tier hard}. \texttt{python run\_baseline.py -{}-capsule capsule-9052293 -{}-tier easy} fetches the capsule (1.0\,MB, cached in \texttt{capsules/}), runs the pipeline of \S3, and writes results to \texttt{results/}. \texttt{-{}-list} prints the selection and capsule sizes without downloading or a key; \texttt{-{}-subset}, \texttt{-{}-tier}, and \texttt{-{}-limit} run batches.

\section{Initial Evaluation Plan}
The iterative system will be compared against this baseline on: (i) official task accuracy (all-or-nothing per task), (ii) per-question accuracy, (iii) wall-clock latency, (iv) dollar cost per task, and (v) failure stage (install, execution, extraction). Published successful tasks averaged \$0.54 versus \$2.59 for failures. The published numbers below (test split, 45 tasks/tier) are the external reference; the benchmark reports no human baseline.

Measured baseline (2 Python capsules, \texttt{claude-sonnet-5}): easy 2/2 = 100\% task and per-question accuracy, \$0.0034 and 3.0\,s per task; hard 0/2 = 0\%, \$0.0049 and 9.7\,s per task, 2/2 failures at execution and none at planning or extraction. The medium tier is not implemented (it needs Docker-in-Docker). The iterative loop will therefore target dependency and invocation repair before answer extraction.

\section{Limitations and Next Steps}
\emph{Dependency rot}: as \S4 shows, the fix can be an older package version, which up-front planning does not recover. \emph{Sample size}: two capsules is a demonstration, not an estimate. \emph{Scope}: GPU and multi-gigabyte capsules are excluded and R capsules (about half of CORE-Bench) are deferred, so results cover only the Python subset. \emph{Retrieval}: the easy tier concatenates result files in directory order up to a character budget, so an answer late in a long log can be truncated. \emph{Stochastic scoring}: with a 95\% prediction interval a faithful reproduction can fall outside by chance, so a perfect agent would not score 100\%. Next: extend to the full Python/CPU test subset, implement the medium tier, add the iterative loop targeting execution-stage failures, and evaluate question-guided result retrieval.
